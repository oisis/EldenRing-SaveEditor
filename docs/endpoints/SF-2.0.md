# SaveForge 2.0 — Architecture Boundaries

## 1. Purpose

This document is the map of the physical boundaries of SaveForge 2.0 inside this
monorepo. It states which directories and files already belong to SaveForge 2.0,
which directories are planned for it, and which existing paths belong to the old
application and must never become a dependency of the new architecture.

It maps versioned repository paths only: the committed paths that belong to
SaveForge 2.0, the paths planned for it, and the explicitly excluded legacy
paths. Local, non-committed working locations are out of its scope and are never
listed as SaveForge 2.0 paths.

The goal is to keep the two architectures physically separated: SaveForge 2.0 is
built greenfield, and the legacy application is research material only. Anyone
adding a file should be able to answer, from this document alone, whether that
file belongs to SaveForge 2.0 and where it goes.

Flags sharing one byte — `4680` and `4681` — are merged into a single write, so the plan `applyByteWrites` receives covers each byte exactly once and rolls every byte back together. No generic dependency, alias or progression-graph layer was introduced. `GetBosses` reads the 110 curated `boss` resources the same way: block `9` was added to that same `resolveEventFlag` at its confirmed BST position, without a second resolver, a separate BST table or an `eventFlagID/8` fallback; block `63` acquisition flags, system flags, unsafe sub-regions, Fog of War and Storage remain untouched. `GetTutorials` reads the 72 titled `TutorialParam` resources and joins their row IDs against the dynamic `TutorialData` list; technical/dummy rows and titleless control prompts are not synthesised, and the reader uses the save-declared payload size rather than a fixed `0x400`. `SetFogOfWarRemoved` is implemented as the one confirmed global operation of that field: `removed: true` fills the 2099-byte bitfield behind the dynamic `UnlockedRegions` list — `afterRegs+0x087E` to an inclusive `afterRegs+0x10B0` — with `0xFF`, in place, with no data shifting, slot rebuild or repacking. It uses no GameCatalog and supports no `MapRegion` resource; `afterRegs` is resolved through the same gesture-anchor and region-count locator `GetRegions` already owns rather than a second layout parser. `removed: false` is rejected fail-closed before the first read, because the bit-to-tile mapping of the field is unknown and zeroing it would destroy the exploration state instead of restoring one; SaveForge 1.5.8 and 1.6.8 are byte-identical here and implemented no inverse either. `SetTutorialUnlocked` stays contract-only and is not exposed over any transport. The remaining contract-only endpoints will require SaveEngine and GameCatalog. |

## 3. Planned SaveForge 2.0 paths

Reserved locations are listed here so that implementation work lands in the
agreed place. No path is reserved at the moment: the SaveEngine paths that used
to be listed here now exist and are described in section 2.

The actual internal split of SaveEngine may be refined once PC and PS4 format differences are
confirmed by evidence. That flexibility applies to SaveEngine internals only:
endpoints must never take over SaveEngine logic, regardless of how SaveEngine is
divided into files.

## 5. Boundary rules

- GameCatalog describes the meaning of game data and stays immutable at runtime.
- SaveEngine is the sole owner of save reading and modification.
- Codec will be the only component with direct access to raw save bytes.
- Endpoints are thin and contain no GameCatalog, SaveEngine or Codec rules.
- One public endpoint lives in one file.
- `LoadSave` creates a session but never modifies the input file.
- SaveEngine supports PC and PS4 container reading and writing; deferred native
  platform checks are tracked in `TODO.md`.
- Swagger is a developer tool; the application frontend does not exist yet and is
  outside the current scope. It may serve the implemented save-session lifecycle
  in its loopback mode only, and it never becomes an application runtime transport.
- Paths under `tmp/` may be used only for local, non-committed development
  research and manual experiments. They must never be a dependency or a
  documented source for committed SaveForge 2.0 application code, test code,
  versioned data, documentation or CI pipelines.
- Do not add new SaveForge 2.0 paths without a prior architectural decision.
